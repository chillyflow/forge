# Spike 004 — can a dense first-byte prefilter make the grammar mask cheap?

**Question.** Spike 003 localized the constrained-decode cost: at full vocabulary
the mask costs **~200 ns per candidate**, flat at ~80 ns until the touched set
stops fitting in cache and doubling afterwards — memory-latency bound, *not*
allocation bound (removing both per-candidate allocations bought only 1.05–1.22×).
Every candidate currently pays `token_to_piece()` (a pointer chase into 151,936
scattered cached strings), a UTF-8 decode, and a grammar walk.

**Idea.** A candidate can only survive if its **first code point** is accepted by
at least one stack position. For an ASCII first byte that test is exactly the byte
test `llama_grammar_match_char()` already performs, so it can be evaluated against
a **dense per-token first-byte table** (1 byte × 151,936 ≈ 152 KB, L2-resident)
*with no pointer chase at all*: build the allowed-byte set once per apply with 256
probes of the *existing* matcher, then reject candidates whose first byte is not in
it, before touching their piece.

**Known limitation, recorded before the run.** This cannot help a state whose
allowed first-byte set is wide — inside a JSON string body (`[^"]*`) almost every
printable first byte is allowed, so nothing is rejected and the cost stays at the
baseline. The states spike 002/003 measured allowed **1–3 tokens out of 151,936**;
that is the population this targets. The end-to-end win is therefore bounded by the
mix of near-forced and permissive states, and this spike measures the two ends
separately rather than claiming one number.

## Pre-registered bar

Frozen before the run. Baseline: spike 003's stock source build
(`run-stock-sizesweep.txt`), same tree, same model, prompt, grammar, `--steps 24`.
The single variable is the patch below.

| # | Hypothesis | Bar | Meaning |
| --- | --- | --- | --- |
| H1 | Near-forced states (root, mid-action — 1–3 tokens allowed) | grammar-only full-vocab apply **≥ 10× faster** (29.00 ms → ≤ 2.9 ms) | the dense reject is the lever |
| H2 | Permissive state | **no worse than 1.2×** regression (P2b: 29.99 ms → ≤ 36 ms) | the fallback is not a tax |
| H3 | Semantics | token-sequence hash identical to `21c6df5710bb7794`; allowed top-20 lists identical on **every** step; top-1 agreement unchanged | exactness |

**Falsifier, stated in advance.** **< 3×** in the near-forced states ⇒ reject this
approach and stop pursuing the mask-cost line; report the state-dependence as the
reason, and re-rank the remaining levers (candidate reduction, config change to
temperature 0, batched candidates).

**Correctness guards the implementation must carry** (they are part of the claim,
not implementation detail): skip the prefilter when the grammar holds a pending
partial UTF-8 sequence (the first byte would be a continuation byte), when any
stack position is a token-id rule (`LLAMA_GRETYPE_TOKEN*` matches by id, not by
character), and for end-of-generation tokens (matched by id, and legitimately
allowed by `allow_eog` even when their piece's first byte is not).

## Method

Patch `src/llama-grammar.{h,cpp}` in the source-mode tree (`build-src`, CPU-only —
no CUDA toolkit on this machine; the mask is CPU work, so the ratio transfers, the
absolute milliseconds do not):

1. `llama_grammar`: a `std::vector<uint8_t> first_byte` built once per grammar
   (0..255 = first byte of an ASCII-leading piece, 0xFF = decide with the full
   decoder), copied by `llama_grammar_clone_impl`.
2. `llama_grammar_apply_impl`: build `allowed_bytes[32]` from the current stacks
   with 256 `llama_grammar_match_char` probes each, then reject candidates on the
   byte test before `token_to_piece()` is ever called.

Run: `forge_sampler_attribution --model <gguf> --prompt <file> --steps 24`

## Results

Run 2026-09-15, source-mode CPU build (`build-src`), same model, prompt, grammar,
`--steps 24`, one variable. Baseline = spike 003's stock run on the same tree.
The patch was generated by `make-patch.py` from the pinned tarball (each edit
asserted to match exactly once) and applied by `git apply` — the numbers below
come from the binary built **from the patch file**, not from hand edits.

**First attempt was a null result, and the reason matters.** The first build
measured *nothing* (24.44 ms vs 25.08 ms baseline). Cause: llama.cpp has **two**
`llama_grammar_init_impl` overloads, and the one that the sampler actually uses
(`vocab`, grammar string, root) constructs its own `llama_grammar` object — the
table was never built, so `prefilter` was always false. A patch that touches only
the rules overload is silently inert. That iteration's medians are quoted here from
the run console (its log was overwritten by the artifact-built rerun that is
retained); the fix was to build the table in the string overload as well.

### Microbenchmark (medians, same tree)

| arm | stock | prefilter | speedup |
| --- | --- | --- | --- |
| P1 `llama_sampler_sample` (Forge's `sampling_ms`) | 25.08 ms | **1.34 ms** | **18.7×** |
| P1 full-vocab chain apply | 23.07 ms | **1.01 ms** | **22.8×** |
| P2 root: grammar sampler alone | 32.06 ms | **0.63 ms** | **50.9×** |
| P2 mid-action: grammar sampler alone | 29.00 ms | **0.64 ms** | **45.3×** |
| P2 post-action: grammar sampler alone | 12.22 ms | **0.53 ms** | **23.1×** |
| P2b permissive grammar, full chain | 29.99 ms | **21.72 ms** | 1.38× |
| P3 ns/candidate at 16,384 | 85.6 | **8.0** | 10.7× |
| P3 ns/candidate at 151,936 | 205.5 | **7.4** | 27.8× |

Semantics: token-sequence hash `21c6df5710bb7794` identical to the stock run,
allowed top-20 lists identical on 24/24 steps, top-1 agreement 15/15, zero
reference-allowed tokens outside the raw top-64. **Exact on this fixture.**

The permissive arm is the honest limitation: inside a state whose allowed first
bytes are nearly all printable characters, the byte test rejects little and the
cost stays near the baseline — 21.7 ms of the 151,936-candidate walk, now the
largest remaining sampler cost.

### End-to-end: Forge's own agent loop, same task, stock vs prefilter

Built from the same source tree; the task is the `calc.py` repair used in earlier
A/Bs, arm A configuration (native protocol, temperature 0.6, `--minimal-agent`).

| arm | generated | decode | tok/s | sampler | sampler share |
| --- | --- | --- | --- | --- | --- |
| stock | 243 tokens | 22,686 ms | 10.7 | 3,872 ms | **17.1 %** |
| prefilter | 243 tokens | 21,079 ms | 11.5 | 1,656 ms | **7.9 %** |

The loop generated the identical 243 tokens. Sampler cost per generated token
fell 15.6 ms -> 6.7 ms (**2.3×**), which is far below the microbenchmark's 18-50×
because the loop's state mix includes permissive states, and on this CPU build
model compute (~85 ms/token) dominates wall clock. On the GPU build, where compute
is ~4.3 ms/token and the same arm measured 71 % sampler share, a 2.3× sampler cut
projects to roughly **1.7× decode** — real, but not the 3× the ~25 ms/token masked
cost suggested, precisely because the permissive half survives the prefilter.

## Verdict

- **H1 met, well above the bar**: 45-51× on the grammar sampler in the near-forced
  states (bar was 10×), 18.7× on the call Forge actually makes.
- **H2 met**: the permissive arm is 1.38× *faster*, not slower — the byte filter
  rejects tokens whose first byte is non-printable and the byte-probe overhead is
  negligible.
- **H3 met**: identical token hash, identical allowed lists, identical top-1. The
  implementation carries the three correctness guards the claim requires
  (pending partial sequence, token-id positions, end-of-generation tokens), and
  handles `LLAMA_GRETYPE_TOKEN` positions exactly by admitting their single token
  id instead of bailing out.
- **The lever is confirmed and measured**: the mask is per-candidate dispatch over
  a scattered piece cache; rejecting on a dense L2-resident byte table takes it
  from ~200 ns to ~7 ns per candidate. The allocation theory (spike 003) was
  wrong; this one is right, and the two spikes together prove which.
- **What it does not fix**: permissive states, where most candidates pass the byte
  test and still pay the piece lookup + decode. That is now the largest remaining
  sampler cost in a real loop, and it is the target for the next spike (a flat
  precomputed code-point table, 2-3 code points per token, to remove the per-
  candidate string lookup entirely), or for bounded candidate reduction with
  spike 002's equivalence evidence.
- **Deployment reality, unchanged from spike 003**: this is inert for
  `FORGE_LLAMA_PREBUILT`, which is what `build-gpu` and the documented release
  flow use. The patch reaches Forge's users through **upstream llama.cpp** (or a
  self-built fork). The patch file, the generator script and these measurements
  are the submission material; per llama.cpp's own contributor rules the
  submission itself is the human's action, not this agent's.
- **Spike-grade caveats, recorded**: the table is rebuilt per grammar object
  rather than cached per vocab; `allowed_ids` is a fixed 8-entry array that
  disables the prefilter when exceeded; a `TOKEN_NOT` position disables it too;
  and the comments are longer than llama.cpp's style. All are review items, not
  correctness holes.
